# Invariants

1. **Presence = managed, per layer.** Every directory with a valid `module.toml` under `modules/`, `hosts/<hostname>/modules/`, or `users/<username>/modules/` is selected unless listed in `disable` or its `when` filter fails. A module existing only in a host or user layer is selected like a base module; a host/user directory with the same name as a base module is its overlay, not a second module. There is no enable list and no `--enable`.
2. **Apply always resumes.** `dotdrift apply` resumes from the step after the last recorded success; the cursor file is deleted on completion, so a completed apply's next run starts from the beginning. No `--resume` flag.
3. **Mise owns files.** Symlink, copy, template, and partial edits are performed only via mise. Dotdrift generates config and invokes mise. Dotdrift's mode vocabulary is exactly mise's (`symlink`, `symlink-each`, `copy`, `template`) and passes through to the generated config unchanged. Apply refuses to clobber pre-existing files mise does not own (a regular file at a symlink target aborts with mise's "refusing to overwrite existing files"; onboard is the deliberate takeover path) unless the user passes `apply --force`, which forwards `--force` to every `mise dotfiles apply` in the run (issue 0046). Copy mode is exempt: file-over-file is an ordinary overwrite, which is also why `--backup` exists only for copy.
4. **State is resume-only.** Persists only `lastCompleted` (the last successfully completed pipeline step); the file is deleted on pipeline completion. No status/error/selection/plan-hash fields.
5. **Onboard materializes then applies.** Copy live paths into the module, write `module.toml`, then immediately run mise dotfiles apply (default mode: symlink). Onboard also **adopts orphans** of the module it materializes: files in the module dir no declaration references (references computed per view, like status orphans) become entries of their own — invertible `home/<rel>`/`system/<rel>` sources map back to `~/<rel>`/`/<rel>` targets, a fully-orphaned directory collapses to one whole-dir entry bounded by all-layer claims and a shared-root blocklist (never `~/.config` and kin), the live counterpart is snapshotted over the stale module copy first (keeping the forced takeover lossless), and file units that would duplicate a claimed target are skipped. A path inside a module layer directory is a directed adoption into that layer's module.toml (no copy). Notices name the layer (`adopted: <target> (<source>) [base|hosts/<hostname>|users/<username>]`); `--dry-run` lists the would-be adoptions without touching anything.
6. **Mise is ensured before use.** Any command that needs mise runs [mise bootstrap](/product/mise-bootstrap.md) first. Every mise subprocess dotdrift spawns — global-state probes and apply-phase operations (install, dotfiles apply, bootstrap, tasks) alike — runs from a pinned neutral working directory (the account's home by default, mise's global-config view): mise loads configs from the cwd upward additively (`--cd` does not suppress them), so a stray or broken `mise.toml` anywhere above the caller's cwd must never leak into dotdrift-driven mise runs (issues 0039, 0041). Hook tasks are unaffected: they anchor `dir = <profile root>` in their task definition.
7. **Exceptions are explicit.** `modules.disable`, `packages.absent`, `--mode copy|template`, host/user overlays. Defaults do the common case. Mount (`[mounts.<name>]`) and Samba (`[smb]`, `[smb.shares.<name>]`) specs in `module.toml` follow the same layer-merge contract as dotfiles: entries merge whole-entry by name, smb scalar fields replace when set, and unset keys fall through to the lower layer's value.
8. **Dotfile sources stay contained.** `dotfiles.<target>.source` is a relative path inside the module directory. A source that resolves outside the layer root (e.g. `../../outside`) is a resolve-time error naming the module and the source. A declared source file that does not exist in any layer is also a resolve-time error (chosen over a warning: fail fast with a clear message instead of dying later inside mise).
9. **Cross-module package conflicts are errors.** If a package is `present` in at least one selected module and `absent` in at least one other selected module, resolve fails with a conflict error naming the package and the modules on both sides. Within a single module, the layer rules still apply: a higher-layer `absent` cancels a lower-layer `present` without error.
11. **Apply serializes on a sidecar lock.** `dotdrift apply` acquires `flock(LOCK_EX)` on `<state-path>.lock` before loading state and holds it until the pipeline's final save or cursor-file removal. The lock never targets the state file itself: `Save` replaces it via atomic tmp+rename, which would orphan an inode-held lock. `Load`/`Save` do no internal locking; callers needing a load→modify→save critical section must hold the sidecar lock. Lock-free readers (e.g. `status`) observe either the complete old or complete new state, and `Save` fsyncs the tmp file before rename for durability.
12. **Hooks are user-declared commands executed as mise tasks.** Modules may declare `[hooks]` `pre`/`post` shell commands in `module.toml`. Layers append (module → host → user) and modules aggregate in selection order — hooks are ordered sequences, not sets. In the apply pipeline `hooks-pre` runs before packages (a pre-hook failure aborts before any side effect) and `hooks-post` runs after dotfiles (a post-hook failure means everything else completed). Each command runs as its own mise task in order; a non-zero exit fails the step and resume re-runs it, so **post-hooks MUST be idempotent**. A hook may set `optional = true` to opt out of fail-fast: its failure is logged at warn and the remaining hooks still run, so a flaky/best-effort hook cannot abort the apply. Required and optional hooks interleave freely — the compact spelling is an inline table in the array (`pre = ["...", { command = "...", optional = true }]`); the table-array `[[hooks.pre]]` form and the bare string array are equivalent alternatives. Hooks run from the profile root with `DOTDRIFT_PROFILE`/`DOTDRIFT_HOSTNAME`/`DOTDRIFT_USERNAME`/`DOTDRIFT_OS`/`DOTDRIFT_BACKEND` in the environment, are visible in `dotdrift plan` (optional hooks marked `(optional)` in text and `"optional": true` in JSON), and can be suppressed with `dotdrift apply --no-hooks` or `DOTDRIFT_NO_HOOKS=1`. When `dotdrift apply`'s stdin is a terminal, the generated hook tasks carry mise's `interactive = true`, so a hook running an interactive command (e.g. `sudo`) is connected to the terminal and can disable echo on its password prompt; with no terminal the tasks run non-interactively.
13. **One apply covers user and system scope.** Scope is module-level (`scope = "user" | "system"` in `module.toml`, `user` when omitted); an unknown value is a resolve-time error naming the module and the value. A single `dotdrift apply` applies user-scope dotfiles as the invoking user and system-scope dotfiles (e.g. `/etc` targets) via a conditional `dotfiles-system` pipeline step. The step splits by entry kind: whole-file entries (symlink-each pre-expanded) and mount destination directories converge through mise's native `[bootstrap.files]` + `[bootstrap.directories]` (`mise bootstrap --only files`) — mise attempts changes as the current user, retries the remainder in one privileged batch with atomic writes, prompts through sudo only on a TTY, and otherwise fails loud with the exact command to run manually (issue 0042; verified against mise 2026.9.1). dotdrift runs **no** sudo for whole-file system entries — symlink→copy is inherent because bootstrap.files manages content, not links. Edit entries have no bootstrap.files equivalent (contract #18): they keep the elevated `mise dotfiles apply` path — the step pre-checks whether every edit target is user-writable and, when any is not (and not already root, EUID 0), converges the edits in a single `sudo -E mise dotfiles apply` pass. Privilege is not otherwise managed: packages self-elevate through their backend (paru/pacman) and hooks carry their own inline privilege (e.g. `sudo` in the command), so neither needs scope machinery.
14. **Placement and activation are separate.** Rendered unit/samba files are placed by mise like any system dotfile; activation (mkdir destinations, daemon-reload, enable/disable, group/user/service/samba-account management) happens in dedicated conditional mounts/smb steps after dotfiles-system, is idempotent, and never writes config files. plan renders mounts/smb sections only when the profile declares them; status reports drift only for declared mounts/smb (sections with no plan items are omitted). Because their artifacts land in root-owned paths, mounts and smb require `scope = "system"` — a user-scope module declaring either is a resolve-time error naming the module.
15. **Generate CLI and wizard are equivalent.** The interactive wizard (huh forms over a pure spec-builder state machine) and the flag-driven CLI mode assemble `generate.Input` through the same shared helpers; the same logical inputs produce a byte-identical module tree either way. The wizard accumulates all mounts/shares and writes once (WriteModule replaces `[mounts]`/`[smb]` wholesale); aborting before the final confirmation writes nothing.
16. **Cross-module dotfile target conflicts are errors.** If two or more selected modules claim the same dotfile target path, resolve fails with a conflict error naming the target and every claiming module. dotdrift emits one `[dotfiles]` table per generated `mise.toml`; a duplicate key would make mise reject the file with a TOML parse error, so dotdrift fails fast at resolve time instead. Within a single module the layer rules still apply: user > host > base for the same target, no error.
17. **`status` is a read-only drift report.** `dotdrift status` compares the resolved plan against the live system (packages, tools, dotfiles, mounts, smb) and never installs, writes, or ensures anything. It exits 0 even when drift is found — drift is reported (`ok`/`drift`/`unknown` per item), the user decides whether to apply. Tools are probed via `mise current`: a tool mise has not installed is drift (`not installed` — apply installs it), a missing mise binary is `unknown` (`mise not available`), an empty version answer is `unknown` (`mise returned no version`), and any other probe failure is `unknown` carrying mise's own error line — never a catch-all (issue 0036). Global-state probes run from a neutral working directory (the account's home, mise's global-config view): a stray or broken `mise.toml` anywhere above the process cwd must not reach them (issue 0039). Symlink sources are validated, not just link targets: a link pointing at the right path whose profile-side source file was deleted is drift (`source missing (dangling link)`), and a symlink-each target-dir link into the entry's source dir whose source was removed is drift (`stale link: source removed`). Whole-directory copy targets compare trees: every file in the source tree must exist at the target with identical content — drift reports counts (`N file(s) missing`, `M file(s) differ`) — while target-only files are not drift, since copy never deletes (issue 0035). File-access probes (readlink, read-file, stat-dir, list-dir) that encounter permission denied (system-scope files under `/etc` and similar) retry elevated via `sudo` for that probe only, so root-owned targets report their real state instead of `unknown`; the elevation is per-probe and transient — no persistent privilege, no full re-run as root. A trailing `orphans` section reports files inside module layer directories that no `[dotfiles]` declaration references. The scan covers EVERY layer directory in the profile — `modules/*`, `hosts/*/modules/*`, `users/*/modules/*` — regardless of the current host, user, or when-filter selection: orphans are profile-content drift, so another machine's leftover shows from anywhere. References come from the layer declarations evaluated per host/user view (whole-entry merge, user > host > base): a directory source references its whole subtree anchored to the declaring layer, marked at declaration time regardless of view overrides (an overlay redeclaring the target wins deployment in its own views, but the declaring tree stays the authored reference — accounts without a user layer resolve the bare-base view the enumeration cannot see; issue 0031); a file source references the file each view resolves to (a base copy shadowed on every host is an orphan, one that still resolves for a host without an overlay copy is not). A symlinked directory that declarations reference through is a container, not an orphan (the walk never descends into it); dangling links and links nothing references through are still flagged (issue 0034). Findings group under layer-root headings (`base` / `hosts/<hostname>` / `users/<username>`) with one `<module>: <file>` line per orphan; the section is omitted when empty and its findings render in a distinct color (magenta) separate from live-system drift hues. After the invoking account's report, a notice lists each OTHER existing OS account that has configuration on this machine (`users/<name>/` with at least one module, or a config-only `dotdrift.toml`) with the exact apply command for it — `sudo dotdrift apply` for the uid-0 account, `sudo -iu <name> dotdrift apply` for any other — plus a reminder that each account needs dotdrift on its PATH (system-wide install, e.g. via mise, system scope). Per-account drift probing was rejected as too noisy to be useful (ADR-0006, issue 0038): no sudo, no per-account mise, no drift sections.
18. **Edit entries are partial edits, any scope.** A `[dotfiles]` key of the form `<file-path>/<edit-id>` (the last slash splits file path from edit id) is an edit entry — a partial edit to a file something else owns — taking `line` (ensure exact line), `block` (optionally `comment`-prefixed, wrapped in mise marker delimiters `>>> mise:<edit-id> >>>` / `<<< mise:<edit-id> <<<`), `source`+`mode = "edit"` (source file's raw contents read at plan time and used as a block — a dotdrift convenience, since mise's `source` alone is a whole-file entry), or `source`+`template` (rendered block, mise renders at apply time). dotdrift generates the `[dotfiles]` TOML and mise applies it; `mode = "edit"` is translated to a mise `block` before emission. Edit entries work at either scope like whole-file entries: user-scope edits apply as the invoking user (`mise dotfiles apply`), system-scope edits apply with root privileges via elevated `mise dotfiles apply` (`sudo`) — `[bootstrap.files]` does file placement, not in-place edits, so the elevated dotfiles-apply path is the only mechanism for system edits (issue 0042 moved whole-file system entries to `[bootstrap.files]`; edits stayed). An edit entry on a file another module claims whole-file is a conflict (contract #16). `status` drift-probes edit entries directly against the live file (bypassing the whole-file source-resolution path): `line` is an exact line match, `block` (including `mode = "edit"`) compares content between markers, `template` checks marker presence only (rendering needs mise's engine — same ceiling as whole-file `template`).
19. **module.toml is strictly schema-validated.** Any key outside the documented schema ([profile layout](/product/profile-layout.md)) is a load-time error naming the file, line, and key (`<path>/module.toml:<line>: unknown key "<key>" [in <table>]`) — typos never decode silently into zero values. The schema is the `profile.ModuleConfig` struct tree enforced at decode; every module.toml read (discovery in all layers, resolve overlays, onboard merge, generate, TUI) applies the same check, so an invalid file fails every command immediately. Structured hook tables accept only `command` and `optional`; secret tables accept only `env`, `description`, and `allow_empty` (with `env` required in every spelling).
20. **`apply --backup` snapshots copy-mode destinations into the profile.** Copy is the only mode whose apply overwrites destination content (symlinks are recreated as links, edits are marker-scoped), so `dotdrift apply --backup` copies every existing copy-mode destination — user and system scope, directories recursively, symlinks followed — into the declaring entry's module layer directory before the pipeline runs: `<module-dir>/backups/<generation>/<absolute-target-path>` (one timestamp generation per run, shared by every module; the declaring layer picks the directory, so a host-won entry backs up under `hosts/<h>/modules/<m>/backups/`). The backup sits next to the profile content that replaces it, and restoring is a plain copy back along the mirrored path. All existing targets are backed up, not only differing ones — a safety net has no diff logic to get wrong; missing targets are skipped; an unreadable target is an error that aborts the apply (the flag must not fail open). No backups without the flag; none when the dotfiles section is deselected (no copy step runs). A `backups/` directory directly under a module layer root is dotdrift runtime output, not profile content: the status orphan scan skips it (deeper `backups` dirs are still content) and onboard never adopts from it — its paths do not invert to live targets.
21. **`restore` is a direct copy-back, no mise.** `dotdrift restore <targets...>` is the inverse of `apply --backup`: it copies backed-up copy-mode destinations from a module layer's `backups/<generation>/` tree back to their live target paths — plain file copies performed by dotdrift itself (like onboard's snapshot), never routed through mise, and never touching pipeline state. Bare `restore` errors: at least one target is required. The mirrored path under a generation directory IS the target (absolute, minus the leading separator); the default generation is the newest holding each target (`--gen` pins one). Restore removes a symlink at the target instead of writing through it, creates missing parents, preserves the backed-up file mode, and restores targets the user cannot write elevated (`sudo install -D -m <mode>`, root-owned result). The same target in two modules' backups is an error naming both. Restored content is expected to drift from the profile: the command says so, and `apply` will overwrite it again — re-onboarding is how restored content becomes the profile's truth.

# Out of scope (v0.1)

- Custom file engine parallel to mise
- Multi-host remote agent
- Hardened apt/dnf production backends (v0.1 ships minimal functional install/remove/is-installed backends, auto-resolved from os-release)
