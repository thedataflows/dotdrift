# Invariants

1. **Presence = managed, per layer.** Every directory with a valid `module.toml` under `modules/`, `hosts/<hostname>/modules/`, or `users/<username>/modules/` is selected unless listed in `disable` or its `when` filter fails. A module existing only in a host or user layer is selected like a base module; a host/user directory with the same name as a base module is its overlay, not a second module. There is no enable list and no `--enable`.
2. **Apply always resumes.** `dotdrift apply` continues from the first incomplete step. No `--resume` flag.
3. **Mise owns files.** Symlink, copy, template, and partial edits are performed only via mise. Dotdrift generates config and invokes mise. Dotdrift's mode vocabulary is exactly mise's (`symlink`, `symlink-each`, `copy`, `template`) and passes through to the generated config unchanged.
4. **State is resume-only.** Persist completed steps, current step, status, error, and selection fingerprint. No content hashes of configs.
5. **Onboard materializes then applies.** Copy live paths into the module, write `module.toml`, then immediately run mise dotfiles apply (default mode: symlink).
6. **Mise is ensured before use.** Any command that needs mise runs [mise bootstrap](/product/mise-bootstrap.md) first.
7. **Exceptions are explicit.** `modules.disable`, `packages.absent`, `--mode copy|template`, host/user overlays. Defaults do the common case. Mount (`[mounts.<name>]`) and Samba (`[smb]`, `[smb.shares.<name>]`) specs in `module.toml` follow the same layer-merge contract as dotfiles: entries merge whole-entry by name, smb scalar fields replace when set, and unset keys fall through to the lower layer's value.
8. **Dotfile sources stay contained.** `dotfiles.<target>.source` is a relative path inside the module directory. A source that resolves outside the layer root (e.g. `../../outside`) is a resolve-time error naming the module and the source. A declared source file that does not exist in any layer is also a resolve-time error (chosen over a warning: fail fast with a clear message instead of dying later inside mise).
9. **Cross-module package conflicts are errors.** If a package is `present` in at least one selected module and `absent` in at least one other selected module, resolve fails with a conflict error naming the package and the modules on both sides. Within a single module, the layer rules still apply: a higher-layer `absent` cancels a lower-layer `present` without error.
10. **Fingerprint scope is broader than selection.** The stored "selection fingerprint" intentionally covers the selected module IDs, the `modules.disable` union, and the facts `hostname`, `username`, `os`, `kernel`, `gpu`, and `backend`. Any change to any of these — not just selection — produces a different fingerprint and resets resume state. Separately, a content hash of the resolved plan (`resolve.PlanHash`, persisted as `state.planHash`) covers the resolved dotfiles/packages/tools/hooks/mounts/smb: editing a module's content with identical selection and facts also resets resume state, so a previously-completed step is re-run and the edited content applies (otherwise a failed apply would leave completed steps skipped on resume, never picking up the edit).
11. **Apply serializes on a sidecar lock.** `dotdrift apply` acquires `flock(LOCK_EX)` on `<state-path>.lock` before loading state and holds it until the pipeline's final save. The lock never targets the state file itself: `Save` replaces it via atomic tmp+rename, which would orphan an inode-held lock. `Load`/`Save` do no internal locking; callers needing a load→modify→save critical section must hold the sidecar lock. Lock-free readers (e.g. `status`) observe either the complete old or complete new state, and `Save` fsyncs the tmp file before rename for durability.
12. **Hooks are user-declared commands executed as mise tasks.** Modules may declare `[hooks]` `pre`/`post` shell commands in `module.toml`. Layers append (module → host → user) and modules aggregate in selection order — hooks are ordered sequences, not sets. In the apply pipeline `hooks-pre` runs before packages (a pre-hook failure aborts before any side effect) and `hooks-post` runs after dotfiles (a post-hook failure means everything else completed). Each command runs as its own mise task in order; a non-zero exit fails the step and resume re-runs it, so **post-hooks MUST be idempotent**. A hook may set `optional = true` to opt out of fail-fast: its failure is logged at warn and the remaining hooks still run, so a flaky/best-effort hook cannot abort the apply. Required and optional hooks interleave freely — the compact spelling is an inline table in the array (`pre = ["...", { command = "...", optional = true }]`); the table-array `[[hooks.pre]]` form and the bare string array are equivalent alternatives. Hooks run from the profile root with `DOTDRIFT_PROFILE`/`DOTDRIFT_HOSTNAME`/`DOTDRIFT_USERNAME`/`DOTDRIFT_OS`/`DOTDRIFT_BACKEND` in the environment, are visible in `dotdrift plan` (optional hooks marked `(optional)` in text and `"optional": true` in JSON), and can be suppressed with `dotdrift apply --no-hooks` or `DOTDRIFT_NO_HOOKS=1`. When `dotdrift apply`'s stdin is a terminal, the generated hook tasks carry mise's `interactive = true`, so a hook running an interactive command (e.g. `sudo`) is connected to the terminal and can disable echo on its password prompt; with no terminal the tasks run non-interactively.
13. **One apply covers user and system scope.** Scope is module-level (`scope = "user" | "system"` in `module.toml`, `user` when omitted); an unknown value is a resolve-time error naming the module and the value. A single `dotdrift apply` applies user-scope dotfiles as the invoking user and system-scope dotfiles (e.g. `/etc` targets) with root privileges via a conditional `dotfiles-system` pipeline step (`sudo -E mise dotfiles apply`, so the generated-config trust environment survives the elevation). When already running as root (EUID 0, e.g. containers) the system step applies directly without sudo. Privilege is not otherwise managed: packages self-elevate through their backend (paru/pacman) and hooks carry their own inline privilege (e.g. `sudo` in the command).
14. **Placement and activation are separate.** Rendered unit/samba files are placed by mise like any system dotfile; activation (mkdir destinations, daemon-reload, enable/disable, group/user/service/samba-account management) happens in dedicated conditional mounts/smb steps after dotfiles-system, is idempotent, and never writes config files. plan renders mounts/smb sections only when the profile declares them; status counts completed steps against the static 8-step pipeline list, so a profile without mounts/smb completes with fewer than 8/8. Because their artifacts land in root-owned paths, mounts and smb require `scope = "system"` — a user-scope module declaring either is a resolve-time error naming the module.
15. **Generate CLI and wizard are equivalent.** The interactive wizard (huh forms over a pure spec-builder state machine) and the flag-driven CLI mode assemble `generate.Input` through the same shared helpers; the same logical inputs produce a byte-identical module tree either way. The wizard accumulates all mounts/shares and writes once (WriteModule replaces `[mounts]`/`[smb]` wholesale); aborting before the final confirmation writes nothing.
16. **Cross-module dotfile target conflicts are errors.** If two or more selected modules claim the same dotfile target path, resolve fails with a conflict error naming the target and every claiming module. dotdrift emits one `[dotfiles]` table per generated `mise.toml`; a duplicate key would make mise reject the file with a TOML parse error, so dotdrift fails fast at resolve time instead. Within a single module the layer rules still apply: user > host > base for the same target, no error.

# Out of scope (v0.1)

- Custom file engine parallel to mise
- Multi-host remote agent
- Hardened apt/dnf production backends (v0.1 ships minimal functional install/remove/is-installed backends, auto-resolved from os-release)
